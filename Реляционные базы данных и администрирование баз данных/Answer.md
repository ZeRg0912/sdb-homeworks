### Задание 1

Опишите не менее семи таблиц, из которых состоит база данных:

- какие данные хранятся в этих таблицах;
- какой тип данных у столбцов в этих таблицах, если данные хранятся в PostgreSQL.

Приведите решение к следующему виду:

Сотрудники (

- идентификатор, первичный ключ, serial,
- фамилия varchar(50),
- ...
- идентификатор структурного подразделения, внешний ключ, integer).

**Ответ:**

1. Сотрудники

Хранит основные данные о сотруднике.
Сотрудники (
 - идентификатор сотрудника, первичный ключ, serial,
 - ФИО, varchar(150) not null

)

Примечание: Я оставил ФИО одним полем, потому что в отчёте оно именно так и хранится.
При желании можно дополнительно разделить на фамилию / имя / отчество.

2. Должности

Хранит справочник должностей сотрудников.
Должности (
 - идентификатор должности, первичный ключ, serial,
 - наименование должности, varchar(100) not null unique

)

Примеры из отчёта:
ведущий QA инженер, специалист, старший инженер, ведущий разработчик.

3. Типы подразделений

Хранит справочник типов организационных единиц.
Типы_подразделений (
 - идентификатор типа подразделения, первичный ключ, serial,
 - наименование типа подразделения, varchar(50) not null unique

)

Примеры из отчёта:
Группа, Отдел, Департамент.

4. Структурные подразделения

Хранит конкретные подразделения организации.
Структурные_подразделения (
 - идентификатор структурного подразделения, первичный ключ, serial,
 - наименование структурного подразделения, varchar(150) not null unique,
 - идентификатор типа подразделения, внешний ключ, integer not null references Типы_подразделений(идентификатор типа подразделения)

)

Примеры из отчёта:
Группа CRM 2, Центр разработки Medio, Департамент FBF.

5. Филиалы

Хранит адреса филиалов, в которых работают сотрудники.
Филиалы (
 - идентификатор филиала, первичный ключ, serial,
 - адрес филиала, varchar(255) not null unique

)

Примеры из отчёта:
Краснодарский край, г. Краснодар, ул Путевая, д. 1
Ростовская обл, г. Ростов-на-Дону, ул 2-я Краснодарская, д. 135/2

6. Проекты

Хранит справочник проектов.
Проекты (
 - идентификатор проекта, первичный ключ, serial,
 - наименование проекта, varchar(200) not null unique

)

Примеры из отчёта:
Севастополь ТВ, Сбербанк Нижний Новгород, Европлан.

7. Кадровые назначения

Хранит кадровое состояние сотрудника: должность, подразделение, филиал, дату найма и оклад.
Кадровые_назначения (
 - идентификатор кадрового назначения, первичный ключ, serial,
 - идентификатор сотрудника, внешний ключ, integer not null references Сотрудники(идентификатор сотрудника),
 - идентификатор должности, внешний ключ, integer not null references Должности(идентификатор должности),
 - идентификатор структурного подразделения, внешний ключ, integer not null references Структурные_подразделения(идентификатор структурного подразделения),
 - идентификатор филиала, внешний ключ, integer not null references Филиалы(идентификатор филиала),
 - дата найма, date not null,
 - оклад, numeric(12,2) not null

)

Примеание: Оклад лучше хранить именно здесь, а не в таблице должностей, потому что в отчёте у одинаковых должностей оклад различается.

8. Назначения на проекты

Хранит связь сотрудников с проектами.
Назначения_на_проекты (
 - идентификатор назначения на проект, первичный ключ, serial,
 - идентификатор кадрового назначения, внешний ключ, integer not null references Кадровые_назначения(идентификатор кадрового назначения),
 - идентификатор проекта, внешний ключ, integer not null references Проекты(идентификатор проекта)

)

Примечание: Даже если в данном отчёте у сотрудника указан только один проект, для нормальной БД связь лучше делать отдельной таблицей. \
Это позволит в будущем назначать одного сотрудника на несколько проектов.


**Такое разбиение убирает дублирование:**

 - должности не повторяются в каждой строке сотрудника;
 - тип подразделения не повторяется в каждой строке подразделения;
 - адрес филиала не повторяется в каждой строке сотрудника;
 - проекты вынесены отдельно;
 - оклад не привязан к должности, потому что одна и та же должность в отчёте встречается с разными окладами.

### Задание 2*

Перечислите, какие, на ваш взгляд, в этой денормализованной таблице встречаются функциональные зависимости и какие правила вывода нужно применить, чтобы нормализовать данные.

**Ответ:**

**Возможные функциональные зависимости в исходной денормализованной таблице**

Обозначим исходную таблицу так:

Отчёт(ФИО, Оклад, Должность, ТипПодразделения, СтруктурноеПодразделение, ДатаНайма, АдресФилиала, Проект)

Для такого отчёта можно выделить следующие зависимости.

1. Сотрудник определяет свои кадровые данные
В рамках данного отчёта фактически:

ФИО сотрудника -> Дата найма, Должность, Структурное подразделение, Адрес филиала, Оклад, Проект

Но в реальной БД ФИО нельзя использовать как надёжный ключ, потому что могут быть однофамильцы. Поэтому в нормальной модели нужен искусственный ключ employee_id.

2. Структурное подразделение определяет тип подразделения

Структурное подразделение -> Тип подразделения

Например, если подразделение называется Группа CRM 2, то его тип — Группа.
Это классическая транзитивная зависимость, которую надо выносить в отдельные таблицы.

3. Должность не определяет оклад

По данным отчёта видно, что одна и та же должность встречается с разными окладами.

То есть зависимости Должность -> Оклад нет.

Следовательно, оклад нельзя хранить в справочнике должностей.

4. Структурное подразделение не определяет адрес филиала

По данным отчёта одно и то же подразделение встречается в разных адресах филиалов.

Значит зависимости Структурное подразделение -> Адрес филиала нет.

Следовательно, филиал нельзя жёстко “вшивать” в таблицу подразделений.


**Какие правила вывода и нормализации здесь применяются**

1. Транзитивность

Если Сотрудник -> Структурное подразделение
Структурное подразделение -> Тип подразделения то по правилу транзитивности Сотрудник -> Тип подразделения

Это означает, что Тип подразделения зависит от сотрудника не напрямую, а через подразделение.

Значит, поле Тип подразделения нужно убрать из основной таблицы сотрудников и вынести в отдельный справочник.

2. Декомпозиция

Исходную широкую таблицу нужно разложить на несколько связанных таблиц:
 - сотрудники,
 - должности,
 - типы подразделений,
 - структурные подразделения,
 - филиалы,
 - проекты,
 - кадровые назначения,
 - назначения на проекты.

Это устраняет избыточность и уменьшает риск аномалий вставки, удаления и обновления.

3. Приведение к 3НФ

Для 3НФ нужно убрать:
 - повторяющиеся справочные значения;
 - транзитивные зависимости;
 - хранение в одной таблице данных разных сущностей.

В данном случае:
 - тип подразделения выносится из общей таблицы, потому что зависит от Структурного подразделения;
 - должность выносится в справочник;
 - филиал выносится в справочник;
 - проект выносится в справочник;
 - связь сотрудника с проектом делается отдельной таблицей.


**Итог по нормализации**
Исходная таблица удобна для просмотра отчёта, но неудобна как структура БД, потому что:
 - одни и те же должности, подразделения, филиалы и проекты дублируются;
 - есть транзитивная зависимость Сотрудник -> Структурное подразделение -> Тип подразделения;
 - невозможно безопасно расширять модель без появления дублей и ошибок обновления.

После нормализации данные логично раскладываются по отдельным сущностям и связываются внешними ключами.
