### Задание 1. Резервное копирование

### Кейс
Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования. 

Необходимо описать, какие варианты резервного копирования подходят в случаях: 

1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.

1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.

1.3.* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.

*Приведите ответ в свободной форме.*

**Ответ**

#### 1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.

Если необходимо восстанавливать данные в полном объёме за предыдущий день, то для этого подойдёт полное резервное копирование. 

В этом случае, например, один раз в сутки создаётся полная копия базы данных. 

Если произойдёт сбой, можно будет восстановить базу из этой копии и получить состояние данных за прошлый день. 

Такой вариант достаточно простой и надёжный, потому что все данные находятся в одной резервной копии, и восстановление выполняется быстрее, чем при более сложных схемах.

#### 1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.

Если необходимо восстановить данные за час до предполагаемой поломки, то одного полного бэкапа уже недостаточно. 

В таком случае нужен полный бэкап вместе с журналами транзакций. 

Сначала создаётся базовая полная копия, а затем отдельно сохраняются все изменения, которые происходят в базе. 

При восстановлении можно не просто вернуть базу на момент последнего полного бэкапа, а восстановить её на конкретный момент времени, например за час до аварии. 

В лекции такой подход связан с восстановлением к определённому моменту времени и позволяет уменьшить потерю данных.

#### 1.3.* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.

Да, такой вариант возможен. 

Для этого используется репликация и отказоустойчивая схема работы. 

Есть основная база данных и одна или несколько реплик, которые получают изменения почти в реальном времени. 

Если основная база выходит из строя, можно переключить систему на реплику и продолжить работу почти без простоя. Но важно понимать, что репликация не заменяет резервное копирование, потому что ошибки или удаление данных тоже могут перейти на реплику.

### Задание 2. PostgreSQL

2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).

2.2.* Возможно ли автоматизировать этот процесс? Если да, то как?

*Приведите ответ в свободной форме.*

**Ответ**

#### 2.1. Пример команды резервирования данных и восстановления БД (`pg_dump` / `pg_restore`)

Для резервного копирования **PostgreSQL** можно использовать утилиту `pg_dump`. 

В официальной документации сказано, что `pg_dump` предназначен для экспорта базы данных PostgreSQL, а архивные форматы дампа потом можно восстанавливать через `pg_restore`. 

Также в документации отмечено, что наиболее гибкие форматы — `custom (-Fc)` и `directory (-Fd)`.

**Пример создания резервной копии:**

```
pg_dump -Fc mydb > mydb.dump
```

Здесь:
 - `mydb` - имя базы данных;
 - `-Fc` - custom format;
 - `mydb.dump` - файл резервной копии.

Формат `custom` удобен тем, что потом дамп можно восстанавливать через `pg_restore` более гибко, в том числе выборочно.

**Пример восстановления базы данных:**

```
createdb restored_db
pg_restore -d restored_db mydb.dump
```

Сначала создаётся пустая база `restored_db`, потом в неё загружается содержимое из дампа. 

В официальной документации `pg_restore` описан именно как утилита для восстановления базы из архива, созданного `pg_dump` в неплоском формате.

Можно привести и самый базовый вариант из документации для обычного SQL-дампа:

```
pg_dump mydb > mydb.sql
psql -X restored_db < mydb.sql
```

В документации раздела SQL Dump именно такая базовая форма и показана: `pg_dump dbname > dumpfile`, а для восстановления текстового дампа — `psql -X dbname < dumpfile`.

#### 2.2.* Возможно ли автоматизировать этот процесс? Если да, то как?

Да, этот процесс можно автоматизировать. 

Поскольку `pg_dump` и `pg_restore` — это обычные консольные утилиты PostgreSQL, их можно запускать из скриптов по расписанию. 

Например, в Linux обычно используют `cron`, а в Windows — «Планировщик заданий». 

Это логично, потому что утилиты работают из командной строки и могут вызываться без ручного запуска.

Например, можно сделать простой скрипт ежедневного резервного копирования:

```
pg_dump -Fc mydb > /backup/mydb_$(date +%F).dump
```

Тогда система будет автоматически создавать резервную копию каждый день. 

При необходимости в такой скрипт можно добавить удаление старых архивов, запись логов и проверку успешности выполнения команды. 

С практической точки зрения это и есть стандартная автоматизация бэкапов.

### Задание 3. MySQL

3.1. С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL. 

3.2.* В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?

*Приведите ответ в свободной форме.*

**Ответ**

#### 3.1. Пример команды инкрементного резервного копирования базы данных MySQL

Если опираться именно на официальную документацию MySQL, то пример инкрементного резервного копирования приводится для утилиты `mysqlbackup` из *MySQL Enterprise Backup*. 

В документации прямо указано, что инкрементный бэкап создаётся с помощью опций `--incremental` и `--incremental-base` либо `--start-lsn`.

Пример команды из официальной документации:

```
mysqlbackup --defaults-file=/home/dbadmin/my.cnf \
  --incremental --incremental-base=history:last_backup \
  --backup-dir=/home/dbadmin/temp_dir \
  --backup-image=incremental_image1.bi \
  backup-to-image
```

Смысл этой команды в том, что создаётся инкрементная резервная копия, то есть копируются не все данные целиком, а только изменения по сравнению с предыдущим успешным бэкапом. 

В документации также сказано, что `--incremental-base=history:last_backup` позволяет взять точку отсчёта из истории предыдущих резервных копий, чтобы не отслеживать её вручную.

Если отвечать проще, то для MySQL инкрементный бэкап в официальной документации связан с тем, что сохраняются изменения за некоторый промежуток времени, а сама возможность такого подхода в MySQL опирается на binary log. 

Документация MySQL Reference Manual отдельно поясняет, что инкрементные бэкапы возможны благодаря включённому бинарному логу, который записывает изменения данных.

#### 3.2.* В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?

Использование реплики даёт преимущество тогда, когда нужно снизить нагрузку на основную базу и не мешать её обычной работе. 

В официальной документации MySQL сказано, что данные можно реплицировать с source-сервера на `replica`, а затем выполнять резервное копирование уже с реплики. 

Это удобно, потому что реплику можно остановить или приостановить для создания снимка данных, не затрагивая рабочую нагрузку на основном сервере.

Ещё реплика полезна в системах, где много операций чтения. 

Документация MySQL указывает, что репликация позволяет распределять запросы чтения по нескольким репликам, за счёт чего увеличивается скорость чтения и уменьшается нагрузка на основной сервер, который занимается записью и обновлениями. 

То есть в такой ситуации реплика даёт не только резервирование, но и выигрыш в производительности.

Также реплика выгодна для аналитики и отчётности. 

По официальной документации, анализ данных можно выполнять на реплике, не ухудшая производительность source-сервера. 

Это особенно полезно, если основная база обслуживает рабочее приложение, а тяжёлые аналитические запросы могут мешать его работе.

Но при этом важно понимать, что реплика не заменяет обычное резервное копирование. 

Репликация нужна в первую очередь для доступности, разгрузки и удобства работы с копией данных, а классические бэкапы всё равно нужны для полноценного восстановления после ошибок, повреждения данных или отката к нужному состоянию. 

В документации MySQL раздел про backups и replication рассматривает эти механизмы как разные инструменты для разных задач.
